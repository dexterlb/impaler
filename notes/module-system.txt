=======================

We define a minimal language (called ILD) with the following (very informally specified) structure:

    Mandatory builtin data types:
        - Symbol: a short string that is used as an identifier
        - Null: has a single inhabitant (null)
        - Pair: a two-element tuple
        - Fail: encapsulates failure, used for poor man's error handling
        - Closure: carries an environment, a list of formal parameters and an expression
        - External value: an opaque value from the environment we're embedded in

    Special forms:
        - quote: returns its argument without evaluating
        - macroexpand: (macroexpand c foo bar baz) gets substituted by the equivalent of (c (quote foo) (quote bar) (quote baz)). A syntax sugar for this special form is available: (!c foo bar baz)
        - lambda: (lambda <params> <body>) creates a closure that captures the current environment and executes <body> with <params> when called

    Mandatory callable external values (every embedding environment must support these):
        - car, cdr, cons
        - null?, pair?, symbol?, fail?, func?
        - make-fail: creates a fail object
        - sym-eq?: compare symbols for equality
        - get-env: get the binding environment of a closure

    Good-to-have external value types:
        - Number
        - Bool
        - String

    And their associated helper callables:
        - number?, add, multiply, num-eq?
        - bool?
        - bool-to-k: converts true to the K combinator and false to the K* combinator
        - string?

    Good-to-have external callables:
        - poly-fix: polyvariate Y combinator; can be implemented by the definition of a Y combinator but in practice it is much more performant to make it available externally
        - eval: of course one could implement an ILD interpretator in ILD, but since this is out of scope, we provide the eval operation externally

We aim to define an ergonomic module system implemented in ILD on top of just
the language features listed here and one additional external callable
(`read-source`, for reading and parsing an external ILD source file).
An example module may look like this:

    (module
        (doc "this module calculates factorials :)")
        (exports main)
        (imports
            (builtin (lambda macroexpand quote <= mul add))
            ("core/prelude.ild" (if)))
        (defs
            (!fn (main) (fact five))

            (!const five 5)

            (!fn (fact x)
                (!if (<= x 0)
                    1
                    (multiply x (fact (add x -1)))))))


We show that the metaprogramming constructs in the minimal language defined
above are sufficient for implementing a "module-loader" function that allows
organising code in such modules. In further research, we aim to show that the
severe performance overhead incurred by implementing such complex
metaprogramming constructs using a very limited set of base special forms can
be significantly reduced by employing partial evaluation as an optimisation
step.



========

Building blocks of the module loader
- letrec: show how to implement a letrec macro using poly-fix
- association lists: note that we need to implement some helper functions for working with association lists
- transforming module definitions to letrec calls
- handling imports (and recursively calling the module loader for imported modules)
