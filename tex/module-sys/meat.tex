Functions in languages such as LISP, Scheme or Racket are \emph{first-class}
objects, meaning that they can be used (placed in data structures, passed as arguments,
returned as values) as any other value~\cite{kohlbecker1986syntactic,r5rs,racket}.
\paraphrase{This} allows for rich abstractions based
on first-class functions
and is a cornerstone of functional programming. Macros, however,
are traditionally not first-class objects:
\begin{itemize}
\item Macro expansion is done in a separate pass before evaluation of the
program begins, and the resulting program has no notion of macros.
\item Macros are defined in their own scope, separate from the scope
of the program.

\item The meta-language of macros may have limited facilities for
introducing new macros within local scopes (e.g. \ild{macrolet} in LISP or
\ild{letrec-syntax} in Scheme), but these bindings are only visible
to other macros and not to the rest of the language.
\end{itemize}
ILD's macro expansion semantics addresses this shortcoming by unifying functions
and macros, thereby granting first-class status to macros.
Instead of tagging applicative objects at bind time to be either
function or macro objects, ILD only supports function objects. Macro expansion via an
ordinary function is triggered at the callsite via the \ildsf{macroexpand}
special form (\cref{macroexpand-mechanism}).
This metaprogramming system has several advantages:
\begin{itemize}
\item Code generated by macro functions can depend on runtime input.
\item A macro function can be used as an ordinary function to operate on
program-like data, for example in bodies of other macro functions (for example,
the usage of \ild{letrec} in \cref{def-eval-module}).
\item The evaluator can be simplified greatly, since the only possible applicatives apart
from special forms are functions
\end{itemize}

Another often-discussed property of macros is \emph{hygiene}: traditional LISP
macros are \emph{unhygienic}, which allows for great flexibility but creates
problems such as accidental capture of identifiers emitted by macros. Other
languages such as Scheme and Racket have \emph{hygienic} macro systems that
employ techniques such as automatic symbol renaming and try to guarantee that macro
expansion is independent of the surrounding environment. These systems are much
more restrictive in expressive power~\cite{bawden-rees-syntactic-closures}.
One of the most commonly-encountered pitfalls of unhygienic macro
systems is accidental namespace capture (or leakage) due to name clashes between
keywords in the surrounding user code and symbols generated by the macro~\cite{kohlbecker1986syntactic,clinger-explicit-renaming}.

Macro expansion in ILD is unhygienic, with similar expressiveness
to traditional LISP unhygienic macro systems. However, ILD macros
are able to avoid a large fraction of the aforementioned namespacing issues by
emitting rich values instead of symbols. This is facilitated by two
properties of ILD:
\begin{itemize}
\item Any value available during ``runtime'' is also available during macro expansion (since
macro expansion \textbf{is} in fact semantically runtime)
\item ILD has no keywords. Special forms like \ildsf{quote} are introduced by a name in
the binding environment (e.g. the \emph{symbol} \ildsym{quote}), but a macro function can emit a combination
with the \emph{special form object} \ildsf{quote} in the head (for example, \cref{lambda-macro-def}). User-introduced
macros, functions and values can also be embedded in the result of a macro function,
instead of their name.
\end{itemize}
To attest to this claim, none of the macros defined in this paper introduce new
symbols in the scope they are called in, and are thus immune to name clash issues.
Nevertheless, it is up to the programmer to use these techniques, and to reach
for \ild{gensym} (\cref{side-effects}) only when they are insufficient.

\subsection{Complex control flow on top of CPS}

ILD's semantics is built on CPS, similar to Scheme. This allows implementing
popular non-linear control flow constructs such as try/catch, early return
and coroutines in the language itself~\cite{r5rs}.

The following example illustrates early return from the recursive computation
enacted by \ild{map}:
\begin{ildcode}
(!fn try-map (f l)
  (call/cc (!lambda (return)
    (return (map
      (!lambda (x)
        (!if (fail? (f x))
          (return
            (make-fail
            (list 'fail-in-element x (f x))))
          (f x))) l)))))
\end{ildcode}
\lstcaption{Early return from \ild{map}}
If \ild{f} returns failure for an item in the list, the subsequent items will not
be processed.
