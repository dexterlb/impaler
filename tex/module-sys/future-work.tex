\section{Future work}
\label{future-work}
Several directions remain open for future work.
\subsection{Optimisations}
This paper focuses on the semantics and expressiveness of ILD and does not attempt
to address performance. To make ILD practical to use, optimisations need to be
put in place.
\subsubsection{Partial evaluation}
In a straightforward implementation of ILD's interpreter, macros are expanded at runtime,
as they are encountered.
This strategy incurs a significant cost, possibly exponential in the depth
of encountered nested macro invocations, since the body of each macro call
is re-evaluated each time the surrounding expression is evaluated. The naïve
ILD interpreter takes approximately one second to evaluate the program from \cref{example-module-fact}
on a modern machine due to expensive macro call reevaluation.
Nevertheless, performance can be greatly improved by evaluating macros ahead of time.
We argue that placing the boundary between code evaluated ahead of time and code
evaluated at runtime should not
follow the distinction between ``macro expansion'' and
``code execution'' drawn by traditional LISP-like languages, but rather the
distinction between ``code dependent on data known ahead of time''
(which includes most, but not all, ILD macros) and ``code dependent on runtime data''.
We aim to explore this topic in further research by applying partial evaluation
as an optimisation pass in ILD, similar to how this has been done in fexpr-based languages
such as Kraken~\cite{fexpr-pe}. In addition to eliminating the overhead
of runtime macro semantics, PE is known to be useful for improving the performance of
non-macro code that does not depend on user input~\cite{anydsl}.
\subsubsection{Tail call optimisation}
Languages such as Scheme, Lisp or Racket support expressing efficient iterative
algorithms as tail-recursive functions, which get optimised into stackless loops
by the interpreter/compiler~\cite{clinger-tail-recursion}. A TCO-enabled ILD evaluator
is worth exploring for similar reasons.
\subsubsection{Module caching}
The simple module loader program presented in this paper evaluates a module every
time it appears in the dependency graph of the root module being loaded.
Due to the lack of mutable module state, this is only an efficiency problem. A less
naïve module loader could traverse the dependency graph ahead of time and
resolve module imports without duplicates.
\subsection{Features}
The \emph{base language} presented in this paper is considered feature-complete. However,
much can be gained by extending the \emph{host environment} and libraries with
more features.
\subsubsection{State management}
\label{side-effects}
The host environment presented in this paper is purely functional and makes no
provision for user-managed state. However, for general-purpose applications,
ILD must be embedded in an impure environment that allows state management and
IO. The CPS calculus of ILD can be extended to model any monadic effect system~\cite[Section 3.3]{wadler}. This includes side effects like IO, and functions
like \(\ildsym{gensym}\):%
\[
\defas{\ildapp{gensym}{s}}{E}{\cpsapp{\cpsret}{\text{a fresh symbol whose
prefix is } s}}
\]

Other functional languages that feature fully-immutable data employ different
methods of handling state, IO and other side effects:
\begin{itemize}
    \item Clojure features immutable core data structures but allows mutable
    state management via object handles such as \code{atom}/\code{ref}:
    the handle itself is immutable, but operations associated with the handle
    may replace its underlying value~\cite{clojure-hist,clojure-atoms}.
    IO operations in Clojure
    also work via similar references. Haskell has a similar
    facility (e.g. \code{IORef}, \code{MVar})~\cite{tackling-awkward-squad}.
    \item Erlang, LFE and other languages on the BEAM virtual machine employ
    processes and message passing as primitives and manage state via an
    actor pattern~\cite{erlang,hewitt-actors}.
    \item User interface DSLs often employ \emph{Functional Reactive Programming},
    where a pure function returning a set of actions to be executed is called by the host
    environment~\cite{hudak-frp,elm-async-frp}.
\end{itemize}
Embedding ILD in environments that provide similar practical features is worth exploring.

\subsubsection{Quasiquote}
ILD's \ildsf{quote} special form yields the given program without
evaluating it. One use of \ildsf{quote} is to let a macro function return
a literal fragment of code as its result. However,
plain \ildsf{quote} does not allow dynamic values to be easily inserted
inside the returned expression. To remedy this, many LISP-like languages
employ a \emph{quasiquote} form that looks for special \emph{unquote} markers
inside the given expression and evaluates the unquoted subexpressions before
splicing them into the result~\cite{bawden-quasiquote}. A similar mechanism can be implemented
in ILD using the metaprogramming techniques shown in this paper.
